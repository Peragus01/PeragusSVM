## Security and correctness

- Sessions kept in memory only. Access and refresh tokens never persisted or logged; reloading requires login. Inactivity/expiry handled with in-memory refresh while page stays mounted.
- Supabase URL/publishable key are browser-public configuration, never service_role or secret keys.
- All protected reads go through the existing same-origin proxy with Authorization bearer; backend enforces identity and ownership.
- Customer history is not stored in global React Query caches; requests abort when the route/account changes.
- Customer API is sandbox-only. provider_completed means sandbox provider state, NOT onchain delivery.
- Indicative amount and converted amount are distinct; unknown amounts remain unknown.
- Wallet connection is NOT identity verification or user authentication. Wallet connector remains Devnet only.
- Invitations, KYC document capture/approval, provider session, customer profile POST, quote, Pix and financial writes remain gated and are not simulated as successful.
- Audit is limited to metadata for authenticated customer-owned operations.

## Local frontend setup (deployment/infrastructure unchanged)

From app/frontend, install dependencies with npm ci; then run npm run typecheck, npm run lint, npm run test, npm run build.

Public frontend variables required for login:

    VITE_SUPABASE_URL=https://YOUR-STAGING-PROJECT.supabase.co
    VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_PUBLISHABLE_KEY

The backend must already authenticate against the same project. Existing Supabase Auth email confirmation and allowed redirect URLs must be configured outside this frontend-only task. Password recovery needs a staging redirect to /recuperar-senha and a compatible recovery email template.
